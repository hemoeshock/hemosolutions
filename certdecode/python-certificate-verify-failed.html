Python CERTIFICATE_VERIFY_FAILED

Python's error message is a wrapper, and the useful part is buried two layers down. Here is how to read it, which trust store Python is actually using, and the correct knob for requests, urllib3, aiohttp, httpx and pip.

Read the whole exception

requests.exceptions.SSLError: (MaxRetryError("HTTPSConnectionPool(host='pypi.org', port=443): Max retries exceeded with url: /simple/ (Caused by SSLError(SSLCertVerificationError(1, '[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer certificate (_ssl.c:NNNN)'))"))

Three layers, and each one adds information:

  1. MaxRetryError — urllib3 gave up after retries. Says nothing about TLS.
  2. SSLError — the TLS handshake failed.
  3. SSLCertVerificationError — verification failed, with the OpenSSL reason in the message: unable to get local issuer certificate, self signed certificate, certificate has expired.

Python exposes the OpenSSL numbers directly on the exception:

import requests, ssl

try:
    requests.get("https://pypi.org/simple/", timeout=10)
except requests.exceptions.SSLError as err:
    cause = err.args[0]
    while cause is not None:
        if isinstance(cause, ssl.SSLCertVerificationError):
            print("verify code:", cause.verify_code)      # the X509_V_ERR number
            print("verify message:", cause.verify_message)
        cause = getattr(cause, "reason", None) or cause.__cause__

verify_code is the same number OpenSSL prints, so you can look it up on the OpenSSL verify code page.

Which trust store is Python using?

This is the single most common cause of "it works on my laptop but not in the container".

ComponentDefault roots
ssl.create_default_context()OpenSSL's default CA paths — SSL_CERT_FILE / SSL_CERT_DIR if set, otherwise the system bundle. On macOS this is not the system keychain.
requests / urllib3The certifi bundle when certifi is installed (which it always is in a fresh virtualenv), otherwise the system store.
pipIts own vendored certifi bundle.

Ask the interpreter what it is actually using:

import ssl
print(ssl.get_default_verify_paths())

try:
    import certifi
    print(certifi.where())
except ImportError:
    print("certifi not installed")

If the venv points at a certifi file inside site-packages, then installing a corporate root into /etc/ssl/certs will not change anything for that venv. You need either REQUESTS_CA_BUNDLE or an explicit verify= path.

requests: the verify parameter

The parameter takes True/False or a path to a CA bundle:

import requests

# one call
requests.get("https://internal.example.com/", verify="/etc/ssl/certs/ca-bundle.pem", timeout=10)

# or for a session
s = requests.Session()
s.verify = "/etc/ssl/certs/ca-bundle.pem"
s.get("https://internal.example.com/", timeout=10)

The file can be a single CA certificate or a bundle of many. If you need the system roots and your corporate root, concatenate them into one file rather than passing only the corporate one:

cat /etc/ssl/certs/ca-certificates.crt corp-root-ca.pem > combined-bundle.pem

Environment variables

export REQUESTS_CA_BUNDLE=/etc/ssl/certs/combined-bundle.pem
# curl's variable is honoured by requests too:
export CURL_CA_BUNDLE=/etc/ssl/certs/combined-bundle.pem

Both are supported by requests and both take a path to a CA bundle. REQUESTS_CA_BUNDLE is the more explicit of the two; CURL_CA_BUNDLE is useful because other tools in the same environment understand it.

When you have no choice but verify=False

There are legitimate short-lived cases — a one-off call against a staging box with a self-signed certificate, before the CA is deployed. If you must:

import requests
import urllib3

urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)

requests.get("https://staging.internal.example.com/", verify=False, timeout=10)

Silencing the warning is fine; leaving verify=False in a code path that runs in production is not. It applies to the whole request, and urllib3's warning exists because the connection is no longer protected against an active attacker.

urllib3 directly

import ssl
import urllib3

ctx = ssl.create_default_context(cafile="/etc/ssl/certs/corp-root-ca.pem")
http = urllib3.PoolManager(ssl_context=ctx)

r = http.request("GET", "https://internal.example.com/")
print(r.status)

You can also pass the file paths explicitly:

http = urllib3.PoolManager(cert_reqs="CERT_REQUIRED", ca_certs="/etc/ssl/certs/corp-root-ca.pem")

Note that PoolManager is created once and reused; creating one per request defeats connection pooling and makes the failure much harder to read in logs.

aiohttp

import aiohttp, ssl

ctx = ssl.create_default_context(cafile="/etc/ssl/certs/corp-root-ca.pem")
connector = aiohttp.TCPConnector(ssl=ctx)

async with aiohttp.ClientSession(connector=connector) as session:
    async with session.get("https://internal.example.com/") as resp:
        print(resp.status)

The same pattern applies to httpx, which accepts a bundle path directly:

import httpx

client = httpx.Client(verify="/etc/ssl/certs/corp-root-ca.pem")
client.get("https://internal.example.com/")

pip

pip is its own client with its own flags and its own variables:

# point pip at a CA bundle
pip install --cert /etc/ssl/certs/combined-bundle.pem some-package

# or set it once
export PIP_CERT=/etc/ssl/certs/combined-bundle.pem

pip also documents --trusted-host (environment variable PIP_TRUSTED_HOST), which marks a host as trusted even though it has no valid HTTPS — it also permits plain HTTP to that host:

pip install --trusted-host pypi.internal.example.com some-package

Prefer --cert. --trusted-host exists for the case where you cannot obtain the CA certificate at all; it removes protection rather than restoring it.

For client certificates — the mirror image of this problem, where you must present a certificate — pip has --client-cert (PIP_CLIENT_CERT), pointing at a single PEM file containing both the private key and the certificate.

Corporate proxies on macOS and Linux

If a proxy re-signs your traffic, its root has to be in the bundle Python reads. The combination that usually works:

# 1. install the corporate root
sudo cp corp-root-ca.pem /usr/local/share/ca-certificates/corp-root-ca.crt
sudo update-ca-certificates

# 2. point Python's clients at a bundle that includes it
export REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt
export PIP_CERT=/etc/ssl/certs/ca-certificates.crt

# 3. if a proxy variable is set, requests will use it
env | grep -i proxy

On macOS, update-ca-certificates is not the mechanism — install the certificate with the security add-trusted-cert command or the Keychain Access UI, and point REQUESTS_CA_BUNDLE at the exported PEM because Python does not read the macOS keychain by default:

security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain corp-root-ca.pem

export REQUESTS_CA_BUNDLE=/etc/ssl/cert.pem

Checklist

  1. Print the exception's verify_code and verify_message — the message tells you which of the three failures you have.
  2. Find out which bundle the failing client reads: certifi.where() for requests and pip, ssl.get_default_verify_paths() for the standard library.
  3. Confirm what the server actually sends with openssl s_client -showcerts. One certificate means the server omitted the intermediate.
  4. Add the CA — as a bundle that includes your public roots, not a replacement file.
  5. Re-run the failing command. Do not repeat the same fix if it still fails; read the new error.
