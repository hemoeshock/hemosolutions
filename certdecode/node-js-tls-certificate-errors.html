Node.js TLS certificate errors

Node.js does not have its own certificate logic — it uses OpenSSL and translates the result into an error with a code property. That code is the key to everything on this page, and Node's trust store is not the operating system's, which is the source of most surprises.

The error codes Node exposes

When a TLS connection fails, the error object carries a code. Print it and you have the diagnosis:

try {
  await fetch("https://internal.example.com/");
} catch (err) {
  console.error(err.code);   // e.g. 'DEPTH_ZERO_SELF_SIGNED_CERT'
  console.error(err.message);
  console.error(err.cause);
}
error.codeMeaningWhere to look
DEPTH_ZERO_SELF_SIGNED_CERTThe leaf certificate is self-signed.Self-signed leaf
SELF_SIGNED_CERT_IN_CHAINThe chain contains a self-signed CA you do not trust.Self-signed in chain
UNABLE_TO_GET_ISSUER_CERTThe issuer could not be fetched.Chain file / network
UNABLE_TO_GET_ISSUER_CERT_LOCALLYNo local copy of the issuer certificate.No local issuer
UNABLE_TO_VERIFY_LEAF_SIGNATUREOnly one certificate was available and it is not self-signed — the server sent just the leaf.Server chain configuration
CERT_UNTRUSTEDThe certificate is marked untrusted in the store.Trust store
INVALID_CAA CA certificate is missing required basic constraints or key usage.CA configuration
CERT_CHAIN_TOO_LONGThe chain exceeds the maximum depth.Server sends too much
PATH_LENGTH_EXCEEDEDA CA in the chain has issued more certificates than its constraints allow.CA configuration
HOSTNAME_MISMATCHCertificate name does not match the requested host.Altname mismatch
ERR_TLS_CERT_ALTNAME_INVALIDThe host name or IP of the peer did not match any subjectAltName in its certificate.Altname mismatch

These are Node's own names for the OpenSSL conditions listed on the verify code page; the mapping is one to one.

Node's trust store is its own

Node ships a bundled copy of the Mozilla CA store and uses that for verification by default — not the operating system's certificate store. Two consequences bite regularly:

  • Installing a corporate root into the OS store fixes your browser and your curl, and leaves Node still failing.
  • Node's bundled store is updated when Node is updated, so a corporate root that expired last week may still be trusted by an old Node build — and rejected by a newer one.

Recent Node.js releases add switches for the other stores. Node 22.4 introduced --use-system-ca, --use-openssl-ca and --use-bundled-ca; run node --help to confirm your build supports them, since older runtimes will simply reject the flag.

Adding a CA: NODE_EXTRA_CA_CERTS

The supported way to add a private or corporate root for a whole process:

NODE_EXTRA_CA_CERTS=/etc/ssl/certs/corp-root-ca.pem node server.js

Details worth knowing:

  • It is additive: the extra certificates sit alongside the bundled Mozilla roots, so public sites keep working.
  • It is read once, at startup. Setting process.env.NODE_EXTRA_CA_CERTS inside the program has no effect.
  • Use an absolute path. A relative path is resolved against the working directory of the process, which is rarely what you meant in a container or a service unit.
  • It applies to everything that uses Node's TLS stack: https, http2, fetch, undici, and the npm client.
  • The file may contain one or many PEM certificates; they are all added.

You can confirm what Node actually trusts at runtime:

const tls = require("node:tls");

console.log(tls.getCACertificates("bundled").length); // bundled Mozilla roots
console.log(tls.getCACertificates("extra").length);   // from NODE_EXTRA_CA_CERTS
console.log(tls.getCACertificates("system").length);  // only with --use-system-ca

If the "extra" count is zero, the variable did not reach the process — check the service manager's environment file rather than the code.

The ca option replaces the default store

Passing ca to https.request, tls.connect or an agent does not add to the bundled roots — it replaces them. Node's documentation is explicit that when ca is specified, the Mozilla CAs are completely replaced.

// Replaces the Mozilla bundle: public sites now fail too.
const agent = new https.Agent({ ca: fs.readFileSync("corp-root-ca.pem") });

// Keeps the defaults: add your CA to Node's bundled roots.
const tls = require("node:tls");
const rootCerts = tls.getCACertificates("bundled");
const extra = fs.readFileSync("corp-root-ca.pem");
const agent = new https.Agent({ ca: [...rootCerts, extra] });

If the second snippet is impractical (a very large bundle, an unusual deployment), the NODE_EXTRA_CA_CERTS environment variable is simpler: it adds to the defaults without you having to enumerate them.

Hostname mismatch: ERR_TLS_CERT_ALTNAME_INVALID

When the error is Hostname/IP does not match certificate's altnames, the certificate was trusted correctly but the name was wrong. No amount of CA configuration fixes this — the certificate must contain the name you are connecting to, in its Subject Alternative Name list.

Check what the certificate actually covers:

openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -ext subjectAltName

Two related traps:

Connecting to an IP address

An IP needs an iPAddress SAN. A DNS: entry with the same text does not match. When you connect to an IP, Node does not send SNI by default; if the server hosts several names, set servername so the right certificate is served:

https.get({
  host: "10.0.0.5",
  servername: "api.example.com",   // sent as SNI
  headers: { host: "api.example.com" }
});

Overriding the identity check

For a controlled test you can override the identity check, but do it only when you already trust the certificate by other means (a pinned key, a private network you administer):

https.get({
  host: "example.com",
  checkServerIdentity: (host, cert) => undefined  // accept any SAN
});

Note that this disables the name check only — chain validation still happens.

Debugging a Node TLS failure

# print the TLS handshake details
NODE_DEBUG=tls node server.js

# show the certificate chain the server sends
openssl s_client -connect internal.example.com:443 -servername internal.example.com -showcerts </dev/null

Two more Node-specific failure modes that look like certificate problems but are not:

CodeWhat actually happened
ERR_TLS_HANDSHAKE_TIMEOUTThe server never completed the handshake — usually a firewall dropping packets, not a trust problem.
ECONNRESET during TLSThe peer closed the connection. Often a proxy or an mTLS requirement the client did not satisfy.
EPROTOProtocol or cipher mismatch: the server wants TLS 1.3 or a specific cipher the client disabled.

Recipes

npm cannot install from an internal registry

NODE_EXTRA_CA_CERTS=/etc/ssl/certs/corp-root-ca.pem npm install

An HTTPS client that talks to one internal host

const https = require("node:https");
const fs = require("node:fs");

const agent = new https.Agent({
  keepAlive: true,
  ca: fs.readFileSync("/etc/ssl/certs/corp-root-ca.pem"),
  // note: this REPLACES the bundled Mozilla roots
});

https.get("https://internal.example.com/health", { agent }, (res) => {
  console.log(res.statusCode);
  res.resume();
});

fetch() with a custom CA

// undici / fetch use Node's TLS stack, so the environment variable is enough:
NODE_EXTRA_CA_CERTS=/etc/ssl/certs/corp-root-ca.pem node app.js

// or with an explicit dispatcher for one call:
const { Agent, fetch } = require("undici");
const dispatcher = new Agent({ connect: { ca: fs.readFileSync("corp-root-ca.pem") } });
await fetch("https://internal.example.com/", { dispatcher });

Never do this

NODE_TLS_REJECT_UNAUTHORIZED=0 node server.js   // disables verification process-wide

This turns every certificate error into a success, for every HTTPS connection the process makes, including calls to third-party services. It also prints a warning to stderr, which is why it shows up in logs and disappears in production where nobody reads them. Use NODE_EXTRA_CA_CERTS instead — it is a one-line change and it keeps verification on.
