unable to get local issuer certificate

OpenSSL error 20 (X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT_LOCALLY) means the client cannot find a certificate for the issuer named in the certificate it received. There are only two reasons: the server did not send the full chain, or the client does not have the CA — usually because something in the middle is intercepting your traffic.

Two causes, one symptom

Cause A: the server sent an incomplete chainCause B: the client does not have the CA
Who is wrong The server. It is missing the intermediate certificate from its configuration. The client (or the network). The CA is missing from the client's trust store.
Typical situation You deployed a new certificate and the old one is still in use, or the server config points at cert.pem instead of fullchain.pem. A corporate proxy inspects TLS; or the tool uses a different trust store than the OS; or the container image has no CA bundle installed.
Who else is affected Every client, everywhere. Browsers fail too unless they cached the intermediate. Usually only the tools that keep their own store (Node.js, Go, Python) or every tool on a machine missing the CA bundle.
Fix Server side: send leaf + intermediates. Client side: install the CA in the store that the failing tool reads.

Diagnose: count what the server actually sent

openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null \
  | grep -c "BEGIN CERTIFICATE"

For a normal public site you expect 2 or 3 certificates: the leaf, one or two intermediates, and occasionally the root. One certificate means the server sent only its leaf and expects you to already know the issuer — which nobody does. That is Cause A.

Then look at the issuer of the leaf:

openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -ext subjectAltName

If the issuer is a well-known public CA but the chain is incomplete, it is Cause A. If the issuer is your company, a proxy vendor, or anything you do not recognise, it is Cause B.

Interception is easy to confirm. Check the issuer and the organisation in the certificate against what you expect. On a TLS-inspecting proxy the leaf certificate is issued to your hostname by the proxy's CA, and it usually names the proxy vendor. You will also find proxy variables in the environment:

env | grep -i proxy

If HTTPS_PROXY is set, every HTTPS request from tools that honour it goes through that proxy.

Fixing cause A: the server sent an incomplete chain

This is the one you can fix without touching a single client. The server must present the leaf and every intermediate up to (but not including) the root. With certbot and Let's Encrypt this is the difference between three files:

FileContentsUse for
cert.pemLeaf onlyNever serve this as the certificate file.
chain.pemIntermediates onlyAppended to the leaf by the server config.
fullchain.pemLeaf + intermediatesThe file the server should point at.

nginx takes both paths and concatenates them:

ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

Apache's SSLCertificateFile expects the same concatenation: cat cert.pem chain.pem > fullchain.pem.

After changing the certificate file, reload the server and re-run the count command above. If it still shows one certificate, the server is serving a cached or different file.

Fixing cause B: the client does not have the CA

Install the CA in the store the failing tool actually reads. This is the part people get wrong: the operating system trust store and the tool trust store are frequently different stores.

ClientWhere it looks for rootsHow to add one
curl Its own bundle path, or CURL_CA_BUNDLE, or --cacert / --capath. curl --cacert ./ca.pem https://host
Git Git's own CA file: http.sslCAInfo, GIT_SSL_CAINFO, or the system store. git config --global http.sslCAInfo ./ca.pem
Node.js Bundled Mozilla store, plus NODE_EXTRA_CA_CERTS. NODE_EXTRA_CA_CERTS=./ca.pem node app.js
Python (requests) certifi bundle (in a venv) or REQUESTS_CA_BUNDLE / CURL_CA_BUNDLE. requests.get(url, verify="./ca.pem")
pip PIP_CERT or --cert. pip install --cert ./ca.pem pkg
Go On Linux: SSL_CERT_FILE / SSL_CERT_DIR, or the distribution bundle (for example /etc/ssl/certs/ca-certificates.crt). On macOS and Windows: the platform verifier and the system store. Linux: export SSL_CERT_FILE=/path/bundle.pem. macOS/Windows: install into the OS store.
Docker daemon Per-registry files under /etc/docker/certs.d/, then the host CA bundle. /etc/docker/certs.d/registry.example.com:443/ca.crt
Java The JRE keystore $JAVA_HOME/lib/security/cacerts, or javax.net.ssl.trustStore. keytool -importcert -alias corp -file ca.pem -keystore "$JAVA_HOME/lib/security/cacerts" -storepass changeit
Browsers The operating system store (Chrome, Edge, Firefox on Linux) or their own store (Firefox). Import the CA into the OS certificate manager; in Firefox also tick "Additional certificates and servers".

Containers and CI runners

Distroless, Alpine and many minimal images ship without a CA bundle, so every HTTPS call inside them fails with this error even though the same call works on your laptop. Fix it in the image, not per command:

# Debian/Ubuntu based
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates \
    && rm -rf /var/lib/apt/lists/*
COPY corp-root-ca.pem /usr/local/share/ca-certificates/corp-root-ca.crt
RUN update-ca-certificates

# Alpine
RUN apk add --no-cache ca-certificates
COPY corp-root-ca.pem /usr/local/share/ca-certificates/corp-root-ca.crt
RUN update-ca-certificates

On Alpine, update-ca-certificates also needs libc6-compat in some base images; if the command fails silently, check that the ca-certificates package is actually installed before you rebuild.

Python virtualenvs specifically

A frequent pattern: the system Python works, a virtualenv does not. The reason is that a venv's pip and requests use the certifi bundle, not the OS store:

python -c "import certifi; print(certifi.where())"
pip install --cert /path/ca-bundle.pem package
export PIP_CERT=/path/ca-bundle.pem

If you want requests to use the system bundle instead, point it there:

export REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt

Verifying the chain by hand

When the chain is incomplete, you can still prove it by asking OpenSSL to verify with the intermediates you supply:

# leaf and intermediates in one file (chain.pem), root separately
openssl verify -CAfile root.pem -untrusted chain.pem leaf.pem

If that prints leaf.pem: OK while the client fails, the server is not sending chain.pem. If it still fails, the problem is the root or the dates, and the error line will tell you which.

Checklist

  1. Count the certificates the server sends. One means an incomplete chain — fix the server.
  2. Read the leaf's issuer. An unfamiliar issuer means interception or a private CA — fix the client.
  3. Compare the issuer in the certificate with the issuer you would expect from DNS. A mismatch is a red flag worth escalating, not a config tweak.
  4. Add the CA to the store the failing tool reads — not "the system store", unless the tool uses it.
  5. Re-run the original command. If it still fails, read the next error code rather than repeating the same fix.
