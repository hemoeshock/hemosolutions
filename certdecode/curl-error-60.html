curl exit code 60, and the rest of curl's TLS codes

curl's exit code 60 means "the peer's certificate or fingerprint failed verification" — and that is all it says. The useful detail is the text that follows in the error line, and curl's verbose output tells you exactly which CA file was consulted while it failed.

What curl tells you

curl: (60) SSL certificate problem: unable to get local issuer certificate

The part in parentheses is the exit code; the part after the colon is OpenSSL's reason, in the same vocabulary as the verify codes page.

The curl TLS exit codes

Codecurl constantMeaning
35CURLE_SSL_CONNECT_ERRORThe TLS handshake failed. Not a certificate problem — look at protocol and cipher mismatches, or a firewall.
53CURLE_SSL_ENGINE_NOTFOUNDThe crypto engine (OpenSSL engine) could not be found.
54CURLE_SSL_ENGINE_SETFAILEDThe crypto engine could not be set.
58CURLE_SSL_CERTPROBLEMProblem with the local certificate — the client certificate you configured.
59CURLE_SSL_CIPHERA cipher could not be used.
60CURLE_PEER_FAILED_VERIFICATIONThe peer certificate or its fingerprint failed verification. Also aliased as CURLE_SSL_CACERT and CURLE_SSL_PEER_CERTIFICATE.
64CURLE_USE_SSL_FAILEDThe requested FTP SSL level failed.
66CURLE_SSL_ENGINE_INITFAILEDThe crypto engine failed to initialise.
77CURLE_SSL_CACERT_BADFILEThe CA cert file could not be loaded — wrong path, wrong format, or unreadable.
80CURLE_SSL_SHUTDOWN_FAILEDThe TLS shutdown did not complete cleanly.
82CURLE_SSL_CRL_BADFILEThe CRL file could not be loaded.
83CURLE_SSL_ISSUER_ERRORThe issuer check failed — added in curl 7.81.0 for stricter issuer validation.
90CURLE_SSL_PINNEDPUBKEYNOTMATCHThe pinned public key did not match the one presented.
91CURLE_SSL_INVALIDCERTSTATUSThe certificate status (OCSP stapling) was invalid.
98CURLE_SSL_CLIENTCERTThe server requires a client certificate and none was accepted.

Note the distinction between 35 and 60. 60 means the handshake got far enough to fetch a certificate and then rejected it; 35 means the handshake never produced a usable certificate at all.

Read the verbose output

curl -v https://example.com/ 2>&1 | grep -E "CAfile|CApath|subject|issuer|SSL certificate problem|server cert|expire date|start date"

Without the grep, a failing request looks roughly like this:

*   Trying 93.184.216.34:443...
* Connected to example.com (93.184.216.34) port 443
* ALPN: curl offers h2,http/1.1
* successfully loaded certificate /etc/ssl/certs/ca-certificates.crt
* CAfile: /etc/ssl/certs/ca-certificates.crt
CApath: none
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.3 (IN), TLS handshake, Server hello (2):
* SSL certificate problem: unable to get local issuer certificate
curl: (60) SSL certificate problem: unable to get local issuer certificate

Three lines do all the work:

  • CAfile: — the bundle curl is verifying against. If it points somewhere you do not recognise, curl is using a different trust store than you expect.
  • CApath: — a directory of hashed certificates, used when --capath is in play. none means only the file above is consulted.
  • SSL certificate problem: … — the actual reason.

When the connection succeeds, the same output also shows the server's certificate:

* Server certificate:
*  subject: CN=example.com
*  issuer: CN=R11
*  start date: Jan  1 00:00:00 2026 GMT
*  expire date: Apr  1 23:59:59 2026 GMT
*  SSL certificate verify ok.

Fixing it

Point curl at the right CA bundle

# a CA file
curl --cacert ./corp-root-ca.pem https://internal.example.com/

# a directory of hashed CA files
curl --capath /etc/ssl/certs https://internal.example.com/

# for the whole session
export CURL_CA_BUNDLE=/etc/ssl/certs/corp-root-ca.pem

Note that --cacert replaces the default bundle rather than adding to it — the same rule as Node's ca option. If you still need to reach public sites in the same shell, build a combined bundle:

cat /etc/ssl/certs/ca-certificates.crt corp-root-ca.pem > combined.pem
curl --cacert combined.pem https://internal.example.com/

Windows builds of curl

The curl shipped in Windows 10 and later uses Schannel, which reads the Windows certificate store — so a corporate root installed there is already trusted. Two Schannel-specific wrinkles:

  • Revocation checking in Schannel is often broken for corporate CAs, producing certificate errors that OpenSSL would not report. --ssl-no-revoke disables revocation checking for that request.
  • --ssl-revoke-best-effort is the softer version: it ignores revocation failures but still checks when it can.

Check which backend your curl uses:

curl -V

The Features line lists Schannel, OpenSSL or LibreSSL — and the Release-Date/SSL backend line tells you which trust store applies.

Debugging one request

To see whether the certificate itself is acceptable, bypass verification for a single call and read the certificate details:

curl -k -v https://internal.example.com/ 2>& | grep -E "subject|issuer|expire date"

-k is --insecure. It applies to that one request, which makes it a reasonable debugging tool and an unreasonable configuration. If you keep it, at least keep it visible in the script that uses it.

Testing a specific IP with the right SNI

curl --resolve example.com:443:203.0.113.10 https://example.com/

This connects to the given IP while still sending example.com as SNI and as the name to verify. It is the fastest way to test whether a problem is DNS or the certificate.

Getting the CA certificate from a server

For a quick test of a server that uses a CA you do not have, fetch the chain and use it as the bundle:

openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null \
  | awk '/BEGIN CERTIFICATE/{n++} n{print > ("cert-" n ".pem")}'

curl --cacert cert-2.pem https://example.com/

This is a diagnostic, not a deployment strategy: you are trusting whatever the server just handed you. Do it to confirm a hypothesis, then get the real CA certificate from whoever runs the server.

curl in a script

Two rules that keep certificate failures loud instead of silent:

# 1. never let a script continue past a TLS failure
curl --fail-with-body --retry 2 --cacert /etc/ssl/certs/combined.pem "$url"

# 2. check the exit code explicitly when the body is empty
if ! curl -sS --cacert /etc/ssl/certs/combined.pem -o out.json "$url"; then
  echo "request failed (curl exit $?)" >&2
  exit 1
fi

Without --fail-with-body curl still exits 0 for HTTP error statuses; without -sS the error message is easy to lose in a log. With -sS, curl's error text goes to stderr and remains visible while stdout stays clean for the response body.
