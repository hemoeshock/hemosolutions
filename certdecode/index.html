TLS certificate verification errors, decoded

Every "certificate verify failed" message is the same three questions asked badly: is this certificate valid, does its name match, and can I build a chain to a CA I trust? This site takes the error strings that curl, Git, OpenSSL, Node.js, Python and browsers actually print, and maps each one to the real cause and the fix that works in production.

The three questions behind every failure

Before you change a setting, work through these in order. Each question has one root cause family, and the fixes in the wrong order usually make things worse.

  1. Is the certificate in its validity window?

    Compare notBefore and notAfter against the current time. A certificate that is "not yet valid" usually means clock skew on the client, a certificate staged too early, or a device with a dead CMOS battery. An expired certificate is a server-side renewal failure — fix the renewal, not the client.

  2. Does the name you used appear in the certificate?

    Modern clients ignore the Common Name and check the Subject Alternative Name list only. https://10.0.0.5/ connecting to a certificate issued for api.example.com fails here even when the certificate is perfectly valid and trusted. This is a name failure, and adding a CA will never fix it.

  3. Can you build a chain up to a CA in your trust store?

    The server sends its leaf certificate and any intermediates. The root is normally not sent — the client is expected to have it already. Chain building fails when an intermediate is missing from the server's response, when the client uses a different trust store than you expect, or when a middlebox replaced the certificate with one signed by an internal CA.

The single most useful diagnostic. It shows what the server actually sent, in order, with the issuer of each certificate:

openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

If the chain you get back is shorter than the chain the server should send, the server is misconfigured — not your client.

How a chain gets trusted

A public TLS certificate is signed up a tree: your leaf certificate is signed by an intermediate, and the intermediate is signed by a root. Your operating system ships the roots; the server ships the leaf and intermediates. Verification walks from the leaf up until it reaches a root it already trusts.

leaf (example.com)          <- signed by
  intermediate (R3)        <- signed by
    root (ISRG Root X1)    <- pre-installed in your OS / trust store

Two consequences explain most of the errors on this site:

  • If the server forgets to send the intermediate, the client holds a leaf signed by an issuer it has never heard of — unable to get local issuer certificate. The chain is incomplete; the CA is fine.
  • If something in the middle (a corporate proxy, a service mesh sidecar, a WAF) terminates TLS with its own certificate, the issuer is an internal CA your trust store has never seen. The certificate may be perfectly valid — for the proxy's name.

What not to do

Every one of these turns a verification failure into a silent security hole. They are fine for five minutes of debugging on a laptop; they are not a configuration to ship.

Tempting shortcutWhat it really doesDo this instead
curl -kDisables peer verification entirely — any MITM can present any certificate.Add the CA with --cacert; keep -k for the one failing request.
requests.get(url, verify=False)Same, plus a urllib3 warning on every call.Pass a CA bundle: verify="/path/ca.pem".
NODE_TLS_REJECT_UNAUTHORIZED=0Node accepts any certificate, for the whole process, including every other HTTPS call it makes.Set NODE_EXTRA_CA_CERTS to the CA you actually trust.
git config --global http.sslVerify falseDisables verification for every repository you clone, permanently.Set http.sslCAInfo for the one CA you need.
pip install --trusted-host …Trusts a host whose TLS may be entirely broken.Pass --cert /path/ca.pem.

Glossary

Leaf / end-entity certificate
The certificate that holds the public key for one hostname. The only one a client actually needs to match against the name it asked for.
Intermediate
A CA certificate that signs other CA certificates. It is part of the chain but not part of the trust decision — the client only needs it to walk upwards.
Root
The self-signed anchor at the top of a hierarchy. It is trusted because it was installed into the trust store, not because the server sent it.
Trust store / CA bundle
The set of anchors a client will accept. Different tools read different files: /etc/ssl/certs/ca-certificates.crt on most Linux systems, the Windows certificate store, certifi in Python, Node's bundled Mozilla store. This mismatch is the root of many "it works on my machine" failures.
SAN (Subject Alternative Name)
The list of names a certificate is valid for. Since 2017 the Common Name is ignored by most clients; if the SAN list does not contain the name you typed, the connection fails.
Chain depth
How many certificates sit between the leaf and the root. OpenSSL reports the depth in its error messages (at 0 depth means the leaf itself is the problem).
