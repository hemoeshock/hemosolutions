Git's SSL certificate problem

Git talks HTTPS through libcurl, so the underlying failure is the same one curl reports — but Git decides which CA bundle to use, and that decision depends on which TLS backend your build was compiled against. On Windows that difference is the whole problem.

The error

fatal: unable to access 'https://git.example.com/team/repo.git/': SSL certificate problem: unable to get local issuer certificate

Everything after SSL certificate problem: is OpenSSL's reason, using the same vocabulary as the verify codes page.

The four settings that matter

SettingEnvironment variableWhat it does
http.sslCAInfo GIT_SSL_CAINFO File containing the certificates to verify the peer with when fetching or pushing over HTTPS.
http.sslCAPath GIT_SSL_CAPATH Directory containing hashed CA certificate files to verify the peer with.
http.sslVerify GIT_SSL_NO_VERIFY Whether to verify the server's certificate. Leave it true; see the warning below.
http.sslBackend GIT_SSL_BACKEND The TLS implementation to use: openssl, schannel, or secure-transport, depending on what the build supports.

Git also supports http.sslCert (GIT_SSL_CERT) and http.sslKey (GIT_SSL_KEY) for client certificates, and http.schannelUseSSLCAInfo for the Windows backend — see below.

The backend split: why Windows behaves differently

Git for Windows is built with Schannel, the Windows TLS stack, which reads the Windows certificate store. Git for macOS is built with SecureTransport, which reads the macOS keychain. A Git built against OpenSSL reads whatever bundle the underlying libcurl is configured with — on Linux, usually the system bundle.

The practical consequence:

PlatformCorporate root installed in the OS storeRoot only in a PEM file
Windows (Schannel)Works out of the box.Needs http.sslCAInfo plus http.schannelUseSSLCAInfo.
macOS (SecureTransport)Works out of the box.Needs the root in the keychain, or a different backend.
Linux (OpenSSL)Only if the OS bundle includes it.Needs http.sslCAInfo.

That last column is the one that surprises people: on Windows, pointing Git at a CA file with http.sslCAInfo does nothing unless you also allow the Schannel backend to use that bundle, because by default Git tells curl not to use it — using it would override the Windows certificate store. The switch is http.schannelUseSSLCAInfo.

git config --global http.sslCAInfo /path/to/corp-root-ca.pem
git config --global http.schannelUseSSLCAInfo true   # Windows only

Check which backend your Git actually uses, and where the setting came from:

git config --show-origin --get http.sslBackend
git config --list --show-origin | grep -i ssl

Fixing it

One-off, without touching your config

git -c http.sslCAInfo=/path/to/corp-root-ca.pem clone https://git.example.com/team/repo.git

This is the right first move: it proves the CA file is the fix before you make it permanent for every repository.

For every repository

git config --global http.sslCAInfo /path/to/corp-root-ca.pem

--global applies to all repositories for the current user; --system applies to all users on the machine; --local (the default) applies to one repository. Use --global for a corporate root, and prefer distributing it with your configuration management tool rather than asking people to run a command.

With an environment variable instead

export GIT_SSL_CAINFO=/path/to/corp-root-ca.pem
git clone https://git.example.com/team/repo.git

Useful in CI jobs and containers, where writing to a user's global Git config is awkward. In a Dockerfile:

ENV GIT_SSL_CAINFO=/usr/local/share/ca-certificates/corp-root-ca.crt

Corporate proxy (the most common case)

If your network inspects TLS, Git needs the proxy's root CA — and every other tool in the pipeline needs it too. On Linux and macOS, install it in the operating system store so that Git, curl, Node.js and your build tools all agree:

sudo cp corp-root-ca.pem /usr/local/share/ca-certificates/corp-root-ca.crt
sudo update-ca-certificates

Then confirm the proxy is actually in the path:

env | grep -i proxy
git config --get http.proxy
git config --global --get http.proxy

A proxy that Git is not using and a proxy that Git is using but that has no certificate in the trust store both produce the same error message.

Seeing the real error

Git's message is a summary. To get curl's full output:

GIT_CURL_VERBOSE=1 git clone https://git.example.com/team/repo.git

You will see the CA bundle Git chose, the certificate the server presented, and the exact OpenSSL reason. For even more:

GIT_TRACE=1 GIT_TRACE_CURL=1 GIT_TRACE_PACKET=1 git clone https://git.example.com/team/repo.git

Those variables are for diagnosis only — GIT_TRACE_CURL prints credentials-relevant detail, so do not paste its output into a public issue or a shared log.

Other Git TLS settings you may need

SettingUse it when
http.sslVersionThe server requires a specific TLS version (for example tlsv1.2). Modern defaults are fine almost always; change this last.
http.sslCert / http.sslKeyThe server requires a client certificate (mTLS).
http.sslCertPasswordProtectedYour client key is encrypted and you want Git to prompt for the passphrase.
http.extraHeaderNot a TLS setting, but it is how you pass an authorisation header for a private Git server.

Git LFS

Git LFS uses Git's own HTTP stack, so it inherits the same CA configuration — but a successful git clone with a failing LFS download usually means the LFS endpoint is a different host with a different certificate. Check what LFS is configured to use:

git lfs env
git config --get lfs.url

Add the CA for that host too, and remember that a proxy intercepting github.com may not intercept githubusercontent.com the same way.

What not to do

git config --global http.sslVerify false
# or
export GIT_SSL_NO_VERIFY=true

This disables verification for every repository you ever clone or push to, permanently and globally, for a problem that usually has a one-line fix. If you are forced to use it for a single emergency operation, scope it to that command with git -c http.sslVerify=false … and write down why.

Checklist

  1. GIT_CURL_VERBOSE=1 — read the real reason and the CA bundle Git used.
  2. git config --list --show-origin | grep -i ssl — see which settings are already in play and where they came from.
  3. Identify the backend: Schannel on Windows, SecureTransport on macOS, OpenSSL on Linux.
  4. Add the CA to the store that backend reads.
  5. Verify with a one-off git -c http.sslCAInfo=… before making it global.
