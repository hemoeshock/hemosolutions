The openssl certificate cheatsheet

Everything you need to look at a certificate: what the server actually sent, who signed it, which names it covers, when it expires, whether the key on disk matches it, and why a chain fails to verify — without leaving the terminal.

1. See what the server sent

openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null
FlagEffect
-servername nameSends SNI. Without it you may get the wrong certificate from a multi-tenant server.
-showcertsPrints the whole chain the server sent.
-verify_return_errorFails the handshake when verification fails, so you see the reason instead of a "successful" connection.
-verify NMaximum chain depth (default 100 is generous; 5 is realistic).
-CAfile fileVerifies against your own bundle instead of the system store.
-tls1_2 / -tls1_3Forces a protocol version — useful when a legacy client is the problem.
-alpn h2,http/1.1Advertises application protocols.

The output ends with a verification summary:

Verify return code: 0 (ok)
# or
Verify return code: 20 (unable to get local issuer certificate)

That number is an X509_V_ERR code — look it up on the verify codes page.

2. Split a chain into individual certificates

openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null \
  | awk '/BEGIN CERTIFICATE/{n++} n{print > ("cert-" n ".pem")}'

for f in cert-*.pem; do
  echo "== $f"
  openssl x509 -in "$f" -noout -subject -issuer
done

cert-1.pem is the leaf; later files are the intermediates.

3. Read a certificate

# the quick look
openssl x509 -in cert.pem -noout -subject -issuer -dates -serial

# everything
openssl x509 -in cert.pem -noout -text

# the names it covers
openssl x509 -in cert.pem -noout -ext subjectAltName

# one specific extension
openssl x509 -in cert.pem -noout -ext basicConstraints
openssl x509 -in cert.pem -noout -ext keyUsage
openssl x509 -in cert.pem -noout -ext extendedKeyUsage

# a fingerprint to compare against something else
openssl x509 -in cert.pem -noout -fingerprint -sha256
FieldWhat to look at
SubjectCommon Name is legacy. Read the SAN list instead — that is what clients check.
IssuerWho signed it. If this names a company you do not recognise, something intercepted your connection.
Not Before / Not AfterThe validity window. Also check the issuer's dates: an expired intermediate breaks an otherwise valid leaf.
Basic ConstraintsCA:TRUE means it can sign other certificates. If a certificate used as a CA says CA:FALSE, you will get INVALID_NON_CA.
Key Usage / Extended Key UsageA leaf must carry serverAuth for HTTPS; a CA must carry keyCertSign.
Authority Information AccessThe OCSP responder and the issuer certificate URL — how you fetch the missing intermediate.

4. Check expiry

# expiry date
openssl x509 -in cert.pem -noout -enddate

# will it expire in the next 30 days? (exit code 0 = yes)
openssl x509 -in cert.pem -noout -checkend 2592000

# will it have expired? (exit code 0 = still valid)
openssl x509 -in cert.pem -noout -checkend 0

-checkend takes a number of seconds. It is the one command worth putting in a monitoring check, because it also tells you about a certificate that is not yet valid — the notBefore in the future is a common surprise after a restore from backup.

5. Verify a chain

# leaf against a root
openssl verify -CAfile root.pem leaf.pem

# leaf against a root, with the intermediates supplied separately
openssl verify -CAfile root.pem -untrusted chain.pem leaf.pem

# also check the name
openssl verify -verify_hostname example.com -CAfile root.pem leaf.pem

# show the chain that was built
openssl verify -show_chain -CAfile root.pem leaf.pem

A successful run prints leaf.pem: OK. A failure prints the code, the depth and the reason:

leaf.pem: error 20 at 0 depth lookup: unable to get local issuer certificate

For a live server, the same thing without files on disk:

openssl s_client -connect example.com:443 -servername example.com -verify_return_error </dev/null

6. Convert between formats

# DER to PEM
openssl x509 -inform DER -in cert.der -out cert.pem

# PEM to DER
openssl x509 -in cert.pem -outform DER -out cert.der

# private key: traditional to PKCS#8
openssl pkcs8 -topk8 -nocrypt -in key.pem -out key-pkcs8.pem

# private key: PKCS#8 to traditional (OpenSSL 3.x)
openssl rsa -traditional -in key-pkcs8.pem -out key-traditional.pem

# protect a key with a passphrase
openssl pkey -in key.pem -aes256 -out key-encrypted.pem

# base64 for copy-paste into a config file
base64 -w0 cert.der        # Linux
base64 cert.der            # macOS: base64 < cert.der | tr -d '\n'

To build a full chain file for a server, concatenate the leaf first and the intermediates after it:

cat cert.pem chain.pem > fullchain.pem

Order matters: the leaf must come first, and the root should usually be left out.

7. Does this key match this certificate?

For RSA:

openssl x509 -noout -modulus -in cert.pem | openssl sha256
openssl rsa  -noout -modulus -in key.pem  | openssl sha256

For EC and Ed25519 keys, compare the public keys:

openssl x509 -in cert.pem -pubkey -noout | openssl pkey -pubin -outform DER | openssl sha256
openssl pkey -in key.pem -pubout -outform DER | openssl sha256

The two hashes must match. A mismatch is the classic cause of a server that serves a certificate the client rejects as "invalid", and of a TLS handshake that fails only after a certificate renewal.

8. Inspect the private key itself

# is it encrypted?
head -1 key.pem
# "-----BEGIN ENCRYPTED PRIVATE KEY-----" means yes

# details (without printing the private material)
openssl pkey -in key.pem -noout -text_pub | head -20

# key size and algorithm
openssl pkey -in key.pem -pubout | openssl pkey -pubin -text -noout | head -3

9. Request and inspect a CSR

# create a key and CSR
openssl req -new -newkey rsa:4096 -nodes \
  -keyout server.key -out server.csr \
  -subj "/CN=example.com"

# what is in the CSR?
openssl req -in server.csr -noout -text
openssl req -in server.csr -noout -subject -verify

Self-sign it for testing:

openssl x509 -req -in server.csr -signkey server.key -out server.crt -days 30

Or sign it with a CA you control:

openssl x509 -req -in server.csr -CA ca.pem -CAkey ca.key -CAcreateserial \
  -out server.crt -days 365 -sha256

10. Revocation status

# the OCSP responder URL from the certificate
openssl x509 -in cert.pem -noout -ocsp_uri

# ask the responder
openssl ocsp -issuer issuer.pem -cert cert.pem -url <ocsp-responder-url> -noverify

OCSP tells you whether a certificate has been revoked. CRL is the older alternative:

openssl crl -in crl.pem -noout -text

Neither mechanism explains most "certificate verify failed" errors — those are trust and name problems, not revocation. But a revoked certificate (CERT_REVOKED, code 23) is worth checking when a certificate was working yesterday.
