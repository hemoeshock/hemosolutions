Let's Encrypt or a private CA?

Choosing a certificate authority is mostly a question about who has to trust you. A public CA asks the whole internet to trust you; a private CA asks your own systems. That difference cascades into cost, automation and every trust error you will ever debug.

The decision in one table

Public CA (Let's Encrypt and friends)Private CA you operate
Names it can certify Public DNS names you control. Wildcards supported. Anything, including internal names and IP addresses.
Who must trust it The entire internet — already true for the root CA. Your own clients. Every one of them needs the root installed.
Validation ACME: the CA checks you control the name. Your policy: whatever your CA is configured to check.
Cost Free. The cost of running the CA and distributing the root.
Typical certificate lifetime 90 days, so automation is mandatory. Whatever you set — often a year, which allows slow manual renewal.
Revocation CRL and OCSP; short-lived certificates reduce how much revocation you need. You define it, including CRLs and short-lived certificates.
Best for Anything on the public internet. Internal services, service meshes, private service-to-service traffic.

When a private CA is the right answer

  • The name is not publicly resolvable — payments.svc.cluster.local, a database replica, an internal admin panel.
  • You want certificates that live for years, so nothing depends on renewal automation being reliable.
  • Your platform already distributes trust: a base image, a configuration management run, an MDM profile. In that world a private CA is nearly free to operate.
  • You want short-lived, automatically-minted identities — the model behind service meshes and SPIFFE — where the CA is the source of identity rather than a certificate of convenience.

The cost of a private CA is not running the CA. It is the trust distribution: every machine, container image, language runtime and third-party tool that has to talk to your services now needs the root. That is the same problem as unable to get local issuer certificate, except now you own it forever.

When Let's Encrypt is the right answer

  • The name is public and you want the world to trust it.
  • You want no CA to operate and no root to distribute.
  • You can run an ACME client on the machine that serves the certificate, or use a hosted automation service.

The trade-off is short lifetimes. Let's Encrypt publishes certificates valid for 90 days, and its guidance is to renew when roughly one third of the lifetime remains — around 30 days before expiry. If your renewal automation can fail silently for a month, you do not want a 90-day certificate.

Let's Encrypt rate limits you will meet

These are global limits, not per-account, and they are the ones that bite people running a fleet of hosts:

LimitValue
New certificates per registered domain 50 every 7 days, counted globally across all accounts. The allowance refills at about one certificate every 202 minutes.
New orders per account 300 every 3 hours, refilling at one order every 36 seconds.
Identifiers per certificate Up to 100 DNS names or IP addresses, depending on the certificate profile selected.
Duplicate certificates for the same exact set of identifiers A small weekly allowance — reissuing the identical certificate repeatedly will hit it.
Authorization failures per identifier per account A handful per hour; repeated failed challenges are counted, not just successes.

Two practical consequences. First, a registered domain means the part you bought from a registrar — example.com, not api.example.com — so fifty certificates a week covers one domain, not fifty subdomains' worth of separate issuance. Second, if you issue one certificate per host rather than one certificate with many SANs, you burn the allowance quickly and hit the duplicate-certificate limit while doing it. Fewer, wider certificates are the better default.

Note that a registered domain for an IP address is treated as the exact address (IPv4) or the containing /64 range (IPv6), which is a consequence of Let's Encrypt issuing certificates for IP addresses.

ACME challenges

ChallengeHow it worksUse it when
http-01 You serve a token at http://domain/.well-known/acme-challenge/…. The default. Port 80 must be reachable from the internet.
dns-01 You add a TXT record for the domain, using an API token for your DNS provider. Wildcards, internal DNS, or no inbound port 80.
tls-alpn-01 You answer the challenge during the TLS handshake on port 443. HTTP is not an option but DNS automation is not either.

Wildcard certificates require dns-01. That means your DNS provider needs an API token, which is a credential with more power than you want lying around: restrict it to the specific zone and to DNS record creation only, never to account administration.

Automating renewal

The rule that keeps outages away: renew early, and make the renewal fail loudly.

# certbot: test the configuration and renewal path without touching the live cert
sudo certbot renew --dry-run

# the systemd timer that ships with most distributions
systemctl list-timers | grep certbot
systemctl status certbot.timer

Four things to get right:

  1. Renew early. A 90-day certificate with renewal starting at 30 days remaining gives you three chances to fix a failure. Renewal at the last day gives you none.
  2. Reload the service after renewal. A renewed certificate on disk does nothing until the server reloads it. Hooks exist for exactly this — --deploy-hook in certbot, --exec /path/to/reload.sh in acme.sh, renewHook in lego.
  3. Check the expiry, not the process. Alert on the certificate's notAfter with a monitoring probe; a renewal job that fails silently looks exactly like a renewal job that is working.
  4. Rehearse it. Run the renewal in a staging environment. Let's Encrypt has a staging environment with its own rate limits and untrusted certificates, specifically so you can test a broken configuration without burning production limits.

Two ACME clients worth knowing:

# certbot — the most widely documented
sudo certbot certonly --webroot -w /var/www/html -d example.com -d www.example.com

# acme.sh — shell-based, popular in containers and with DNS API plugins
acme.sh --issue --dns dns_cf -d example.com -d '*.example.com' --keylength ec-256

When you use dns-01 with a wildcard, remember that the wildcard certificate also needs the base domain in the same certificate, and that the DNS API token is the credential you now have to protect.

Private CA automation

If you run your own CA, the same discipline applies with a different tooling vocabulary. Certificate authorities like step-ca and Smallstep's tooling, or Vault's PKI secrets engine, all issue certificates from an API and can revoke them. What you must build yourself is the second half of the system: distributing the root to every client that needs to verify you.

That distribution is where private CAs usually fail in practice:

  • Base images built before the root existed, never rebuilt.
  • Developer laptops that trust the production CA, or worse, trust a throwaway dev CA that is still in the trust store after the migration.
  • Tools that keep their own store — Node.js, Go, Python's certifi — which are not covered by an OS-level trust install.
  • Certificates issued by an intermediate whose root is installed but whose intermediate is not sent by the server — the incomplete chain problem, entirely self-inflicted.

Two mitigations that work well: issue directly from the root (one level, nothing to omit) or serve the full chain every time; and make trust installation part of the machine or image build, not a runbook step.

A practical hybrid

Most mature environments run both:

SurfacePKI
Public websites and APIsLet's Encrypt, renewed automatically
Internal service-to-service trafficPrivate CA with short-lived certificates
Local developmentA local development CA whose root is installed on developer machines only
Hardware and offline devicesPrivate CA with long lifetimes and a manual revocation process

The rule of thumb: if a certificate's audience is "everyone", use a public CA. If its audience is "systems you administer", a private CA is cheaper and safer.
