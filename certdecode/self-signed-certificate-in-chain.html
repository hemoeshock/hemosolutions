self signed certificate in certificate chain

The server sent you a chain that ends in a self-signed certificate, and you do not trust that certificate. The fix is not to stop verifying — it is to decide who should trust that CA, and then make that happen in one specific place.

What the message really means

TLS verification is a chain-building exercise. The server presents its leaf certificate and, usually, the intermediates. The client walks up that chain until it reaches a certificate it already trusts — the anchor. Two OpenSSL codes produce almost identical wording, and telling them apart tells you what to fix:

OpenSSL codeMeaningWhat it tells you
18 — DEPTH_ZERO_SELF_SIGNED_CERT The leaf certificate itself is self-signed. There is no issuer above it at all. Nobody signed this certificate. Only a self-signed anchor can be trusted directly, and this one is not in your store.
19 — SELF_SIGNED_CERT_IN_CHAIN The chain contains a self-signed CA certificate, but that CA is not trusted by your client. The chain is well-formed. You just need the CA to be trusted, or the server to send a different chain.

The wording "self signed certificate in certificate chain" is the depth-zero case too in some OpenSSL versions, which is why people read it as "the server sent a self-signed cert". Check the number in the error line rather than guessing from the prose: error:18 at 0 depth lookup and error:19 at 0 depth lookup need different fixes.

Diagnose it in one command

openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

Read the chain top to bottom. For each certificate, print its subject and issuer:

openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null \
  | awk '/BEGIN CERTIFICATE/{n++} n{print > ("cert-" n ".pem")}'

for f in cert-*.pem; do
  echo "== $f"
  openssl x509 -in "$f" -noout -subject -issuer
done

The first file (cert-1.pem) is the leaf; each following one is an issuer. The last one in the chain is either a root you should already trust, or the self-signed CA that is causing the error.

Three outcomes:

  • You get one certificate whose subject equals its issuer, and it is not in your trust store → the depth-zero case. The certificate was never issued by anyone you know.
  • You get a leaf plus a self-signed CA at the end, and that CA is not in your trust store → the "in chain" case. Add that CA to the store.
  • The chain ends at a public root you do recognise → you have a different problem: something is rewriting the chain. See unable to get local issuer certificate.

The four real situations, and the fix for each

1. A developer machine talking to a local dev server

The normal cause. Your colleague ran openssl req -x509 or a container generated a throwaway certificate. The right answer is a local certificate authority: generate one root, issue every dev certificate from it, and install the root into the trust store of the machines that need it. mkcert automates exactly this and handles Firefox separately from the OS store.

Do not hand out the root of a production CA for this, and do not disable verification to make it work.

2. A corporate TLS-inspecting proxy

Your network terminates TLS with its own certificate, signed by an internal root CA. That root is not in your store, so every client that does not have it reports a self-signed or unknown-authority error — for every host, not just one.

The fix is to install the organisation's root CA into the operating system trust store (usually distributed by IT) and into the trust stores of tools that do not use the OS store, such as Node.js and Go. If you cannot get the root, no application-level setting will make the connection work.

3. An internal service with a private CA

Your own CA issues certificates for service.namespace.svc and friends. Clients must trust your root. Options, in rough order of preference:

  • Distribute the root through your platform's trust management (systemd trust store, container image build, base image, MDM). One source of truth, no per-tool configuration.
  • Point individual tools at a CA bundle file when you cannot change the platform.
  • Use SPIFFE/SVID or mTLS with your own verifier if the consumer is under your control — you can verify against your own root explicitly instead of changing global trust.

4. A public website

A self-signed certificate on a public name is simply wrong. Issue it from a public CA instead — see Let's Encrypt vs a private CA for how to pick and automate one.

Per-tool fixes

Each of these makes the client trust one additional certificate authority. None of them disables verification.

curl

# a single CA file
curl --cacert ./corp-root-ca.pem https://internal.example.com/

# a directory of hashed CA files (what OpenSSL's CApath expects)
curl --capath /etc/ssl/certs https://internal.example.com/

# for the whole session
export CURL_CA_BUNDLE=/etc/ssl/certs/corp-root-ca.pem

Node.js

# adds a CA to the bundled Mozilla store, for the whole process
NODE_EXTRA_CA_CERTS=./corp-root-ca.pem node server.js

In code, the ca option of https.request / tls.connect replaces the default Mozilla bundle rather than adding to it. If you pass ca, include the public roots too if you still need to reach the public internet from that process. More on Node.js specifics.

Python (requests)

import requests
requests.get("https://internal.example.com/", verify="./corp-root-ca.pem")

# or for a whole session:
# export REQUESTS_CA_BUNDLE=./corp-root-ca.pem

pip

pip install --cert ./corp-root-ca.pem some-package
# or: export PIP_CERT=./corp-root-ca.pem

Git

git config --global http.sslCAInfo ./corp-root-ca.pem
# one-off, without changing config:
git -c http.sslCAInfo=./corp-root-ca.pem clone https://internal.example.com/repo.git

Go

export SSL_CERT_FILE=/path/to/corp-root-ca.pem   # replaces the bundle file
export SSL_CERT_DIR=/path/to/hashed-ca-dir        # or adds a CApath

Go on macOS and Windows verifies through the platform verifier and the system certificate store, so SSL_CERT_FILE has no effect there — install the CA into the operating system store instead. On Linux, SSL_CERT_FILE replaces the bundle entirely, so point it at a concatenated bundle rather than a single CA.

Docker daemon (image and registry pulls)

sudo mkdir -p /etc/docker/certs.d/registry.example.com:443
sudo cp corp-root-ca.pem /etc/docker/certs.d/registry.example.com:443/ca.crt
sudo systemctl restart docker

Why "just disable verification" is worse than the error

Disabling verification does not make the certificate valid — it makes the client stop asking. From that moment on, anything that can intercept your traffic can present any certificate it likes and you will connect to it happily. With verification on, the failure is loud and harmless; with verification off, the failure is silent and total.

If you must bypass verification for a single debugging step, keep it to one command with an explicit flag, and never promote it to configuration.

Checklist before you close this out.

  1. The chain you inspected is the chain the server really sends (see the s_client -showcerts output above).
  2. You identified the CA that signs the leaf, and you know whether it is a public root, a corporate root or your own.
  3. You added exactly that CA — not "the whole bundle from a colleague's laptop".
  4. You added it in the trust store the failing tool actually reads.
  5. No verification-disabling flag was left behind.
